    README¶

    @iswesolutions/odoo-proxmox-runbot

    A Backstage page for running Odoo on Proxmox VE. It brings together three things an Odoo hosting team juggles:

    • Odoo instances, each in its own Proxmox LXC container
    • Runbot CI builds for the Odoo, Enterprise and custom-addon repositories
    • Ansible playbooks that install, configure, back up and upgrade those instances

    Preview. The page and its services are a working UI, but the services return built-in sample data, except the Runbot tab, which is live (see below). Nothing is sent to Proxmox or Ansible yet, and the plugin reads no configuration. Use it to evaluate the workflow, not to manage real instances. See Status.

    The page

    The page has five tabs.

    Tab What it shows
    Dashboard Counts of instances, running instances, Runbot builds and Proxmox nodes; cluster CPU, memory and storage usage; recent builds; and a table of instances to open
    Instances Every instance with its status (running, stopped, provisioning), version, edition, node and resources. Actions: start, stop, back up, clone, settings and delete
    Runbot Live, from the odoo-runbot backend: projects, bundles (branches and pull requests across repositories) with their latest batch and one build per trigger, builds with live logs, repositories and triggers, and builders. Add repositories, rebuild, kill, force a batch
    Ansible Playbooks and their execution history: status, duration and per-host stats (ok, changed, failed, unreachable). Run a playbook from here
    Proxmox Each cluster node's CPU, memory and storage usage
    Creating an instance

    New instance opens a five-step form. The Review step lists anything that must be fixed, and Create instance stays disabled until it's clean.

    1. Basics: - name: gives the container hostname - domain - environment: production, staging or development - Odoo version and operating system: only valid pairs are offered (see below) - edition and Proxmox node - CPU cores, memory and storage
    2. Sources: where the code comes from. - Odoo's repository and branch, tag or commit. - For Enterprise, its repository, or your mirror of it. - Any number of addons repositories, each with a revision and an optional sub-folder. Their order is the search order. - Repositories can be picked from the catalog: any Component tagged odoo that has a github.com/project-slug annotation. - The resulting addons_path is shown below the list: Enterprise, then the addons repositories in order, then Odoo's own addons.
    3. Database: a shared PostgreSQL cluster (recommended) or a local server in the container. - The cluster follows the environment: production uses prod, staging stg, development dev. - The role is <database>_app, with a generated password. - The connection uses sslmode=verify-full.
    4. Configuration: odoo.conf, in groups: performance, security, email, logging and other, plus free-form options. - The settings are suggested from the container's size and the environment until you edit them. Suggest from size recalculates them.
    5. Review: problems, then the resulting odoo.conf. Secrets appear as placeholders.

    Versions and operating systems:

    Odoo Runs on Note
    19.0 Ubuntu 24.04 (Python 3.12)
    18.0, 17.0 Ubuntu 24.04 or 22.04
    16.0 Ubuntu 22.04 (Python 3.10) No longer supported by Odoo S.A.; allowed with a warning

    Suggested settings:

    • Workers: 2 × cores + 1, capped by memory: 512 MB is kept for the system, and each worker is allowed about 400 MB on average. Development runs threaded (0 workers), which is simpler to debug.
    • Memory limits: 80% of the container's memory, shared across workers and cron threads, between 640 MB and 2 GB each. The hard limit is 1.25 × the soft limit.
    • Time limits: 600 s CPU and 1,200 s real, so large imports and reports finish.
    • Connections: 16 per process on a shared cluster, 64 on a local server.

    Safe defaults, and what the form enforces:

    Setting Production Staging Development
    list_db (database manager) off; error if on off; warning if on on
    dbfilter ^%d$; error if .* ^%d$; warning if .* .*
    Demo data none; error if loaded none allowed
    proxy_mode on (behind nginx); warning if off on on
    Master password generated and stored, never shown. A typed one must be at least 16 characters same same

    Database names on a shared cluster follow <owner>_<app>[_<part>]:

    • lowercase snake_case, at most 40 characters
    • no environment in the name (_prod, _test, _dev…): the cluster is the environment
    • no version or year; _demo and _training never in production

    These are errors on a cluster, and only advice for a local database.

    Other checks:

    • an addons branch for a different Odoo version
    • a cluster that belongs to another environment
    • memory limits that overcommit the container
    • the Enterprise edition without an Enterprise repository

    Creating an instance is meant to run these steps in order:

    1. Take the next free VMID from Proxmox.
    2. Create an unprivileged container from the chosen OS's template.
    3. Run the odoo-install playbook. Its variables come from installPlaybookVars(): - odoo_version, odoo_repo_url/_rev, odoo_enterprise_repo_url/_rev - odoo_addons_repos and odoo_config_addons_path - the database connection, with odoo_install_postgresql true only for a local server - one odoo_config_<option> per odoo.conf setting
    4. Run the nginx-proxy playbook to put the instance behind nginx with TLS (port 8069, WebSocket/longpolling on 8072).

    If a step fails after the container exists, the error names the container so it can be cleaned up or provisioning retried.

    The rules live in src/odooConfig.ts as pure functions, and are exported for reuse:

    • ODOO_VERSIONS, OS_INFO
    • computeAddonsPath, suggestServerConfig
    • checkDatabaseName, validateCreateRequest
    • renderOdooConf, installPlaybookVars
    Playbooks

    The Ansible playbooks ship in this package, in ansible/, and work with or without Backstage. odoo_platform chooses where an instance runs:

    odoo_platform The guest
    proxmox An LXC container on a Proxmox VE cluster
    lxd An LXD container
    docker A Docker container running systemd
    ssh An existing machine
    Playbook Purpose
    odoo-install Create the guest, then install Odoo: code, Python, wkhtmltopdf, database, odoo.conf, service
    odoo-configure Rewrite odoo.conf and the service unit; restart if they changed
    nginx-proxy nginx with WebSocket; TLS from Let's Encrypt, your own certificate, or none
    odoo-backup Database, filestore, odoo.conf and code revisions
    odoo-restore Restore a backup, after a safety backup
    odoo-upgrade Update the code and modules within one major version
    odoo-remove Delete the guest; needs a confirmation naming the instance

    installPlaybookVars() sends the guest's settings with each request: name, OS, cores, memory, disk, node and domain. The platform and its credentials belong to the backend's inventory, not to the request.

    Runbot

    The Runbot tab is a client of the ISWE Runbot backend (@iswesolutions/plugin-odoo-runbot-backend): continuous integration for Odoo repositories after odoo/runbot. Install the backend and at least one builder (ansible/playbooks/runbot-builder.yml); see the backend's README.

    To test a repository:

    1. New project, e.g. ISWE Odoo 19, base branch 19.0.
    2. Add repository odoo/odoo, as the one providing odoo-bin.
    3. Add repository for each addons repository, for example ISWE-Solutions/iswe_meal_addons, ISWE-Solutions/iswe_sdp_addons and ISWE-Solutions/ZRA-Smart-Invoice-Odoo19. You can pick them from catalog components tagged odoo. Leave install and test on: that creates a trigger which installs its modules with odoo 19.0 and runs their tests on every push and pull request.

    Each repository's main joins the 19.0 base bundle. A feature branch or pull request gets its own bundle, built on 19.0. Results show as GitHub commit statuses (ci/runbot-<repository>) that link back to the build here (/odoo?runbotBuild=<id>).

    Installation

    The package is a frontend plugin for the legacy (non-/alpha) Backstage frontend system.

    yarn --cwd packages/app add @iswesolutions/odoo-proxmox-runbot

    // packages/app/src/App.tsx
import { OdooPage } from '@iswesolutions/odoo-proxmox-runbot';

<Route path="/odoo" element={<OdooPage />} />;

    // packages/app/src/components/Root/Root.tsx
import CloudIcon from '@material-ui/icons/Cloud';

<SidebarItem icon={CloudIcon} to="odoo" text="Odoo" />;

    No app-config.yaml settings, backend plugin or proxy endpoints are needed. The create form reads the software catalog (catalogApiRef, present in every Backstage app) for addons repository suggestions; if the catalog can't be read, repositories are typed in.

    Services

    All methods are async.

    Service Methods
    odooService getInstances, getInstance, createInstance, updateInstance, deleteInstance, startInstance, stopInstance, restartInstance, backupInstance, restoreInstance, upgradeInstance, cloneInstance, getInstanceModules, installModule, uninstallModule, getAvailableVersions, getDashboardStats
    ansibleService getPlaybooks, getPlaybook, executePlaybook, getExecutions, getExecution, cancelExecution, getInventoryHosts, getRoles, validatePlaybook, testConnection
    proxmoxService getNodes, getContainers, getNodeContainers, getContainer, createContainer, startContainer, stopContainer, restartContainer, deleteContainer, cloneContainer, resizeDisk, getTaskStatus, getTemplates, getNextVmid, execCommand

    odooService orchestrates the other three: creating, cloning or upgrading an instance calls proxmoxService and ansibleService.
